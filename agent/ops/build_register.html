Getting call sheets to callers — solved and proven

Working
How
One workbook per caller, attached to a Gmail draft. Tested end to end: Kharen's 200 numbers, 8.5KB, opened cleanly with the leading zeros intact.
Why not work email
The work account is Microsoft (brendon@pacificlinkglobal.com) and it is connected — but none of the three Outlook write tools can attach a file. Gmail's draft call takes attachments up to 25MB.
Now going further
Email delivers a file; it does not bring one back, and callers have to record outcomes as they work. So call sheets move to SharePoint, where they are edited in place — which is what already happens today, just without one workbook shared to everybody. "Anyone with the link, can edit" needs no Microsoft account, and unlike Google Drive the links are revocable and can expire.
Shape
One folder per caller, shared once, permanently. Poll and date live in the filename, so a caller working two polls in a day sees two clearly-named files. Twenty shares, once, instead of forty every day.
Isolation
Not in the main site — that one holds invoices, contracts and GST receipts. A separate SharePoint site keeps external sharing switched on in one place only. Site creation is manual: there is no such call in the connector. Everything inside it — folders, uploads, updates, reading back what callers typed — is automatic.
Side benefit
Each caller receives only their own numbers. The shared 20-tab workbook exposed everyone's list to everyone.

SharePoint folders can be built but not shared

Blocked 30 manual shares, once
Why
The M365 connector has create_folder, upload_file, move_item, copy_item, rename_item and delete_item — and no permission or sharing call at all. Checked against the full tool surface, not assumed. So the agent can build the whole structure and cannot grant one person access to it.
Mirror image of Drive
On Google Drive the agent can grant access and never revoke it. On SharePoint it can do neither. Both halves of sharing are manual.
Why it is survivable
This is exactly why folder-per-caller beats folder-per-date. Thirty shares, once, forever — against twenty to forty every single day under the other shape. A one-off cost is the difference between a system that runs and one that quietly stops.
How to share correctly
"Specific people", never "Anyone with the link" — the latter is forwardable and is how the Google call sheets ended up open to the world. Share the individual folder, never the parent Call Sheets folder, or everyone gets everyone's numbers.

Seeing who is available — solved twice over

Solved
Why
A poll arrives through the API as type: "poll_creation" carrying the question and options — and nothing else. There is no voter list on the object. This is WhatsApp, not the connector; no plan upgrade changes it.
Instead
Text replies are readable, and every reply already carries its sender. So the question goes out as an ordinary message and from_chat_replies reads the answers — 13 14 15, Sun Mon Tue, Mon-Thu, all week, Mon Tue Wed but not Wed, not available. Better than a poll: nobody types their own name, which is where the spelling mess was being created.
Better still
Standing patterns read from six months of audit history cover 4 of the 5 days without asking anyone anything. The weekly question shrinks to the days that come up short.
Ruled out
lharries/whatsapp-mcp — its own README warns it is subject to the lethal trifecta: private data, untrusted content from 90 group members, and the ability to send. It is also local-only, so it could not reach a chat session. The WhatsApp Business API is official and safe, but cannot do group chats and takes the number over from the normal app.
Slack fixes it
The Slack connector is now live — 27 tools. slack_get_reactions returns the users who reacted, with names and ids. So an emoji reaction is a readable, attributed vote: post the days, people tap, the agent reads exactly who tapped what. That is the thing WhatsApp refused to give — and no poll app, no Simple Poll, no Polly, no paid tier.
Proven live
Tested end to end on 10 September, not assumed. Five day messages were posted to #availbility-pacificlinkglobal, both emoji pre-seeded on each, and the reactions read back: :white_check_mark: × 1 — Brendon Duong (U0C0U8P4T0W). Emoji, count and the named voter. The loop works.
Design that fell out of it
One message per day, not one per week. That yields three states per person per day — tapped yes, tapped no, tapped nothing — and the third is the valuable one: it separates a caller having a quiet week from a caller who has drifted off. Both emoji are pre-seeded so voting is one tap rather than a hunt through the emoji picker, which is where mobile adoption dies. Cost: the agent's own tap counts in every total and must be subtracted.
Ruled out
Slack Lists and canvases — both unavailable on a free workspace. The instructions therefore live as pinned messages, which the 90-day limit below will eventually eat, so they need re-posting.
What protects us
Read-only, plus draft everything, send nothing. Untrusted text can reach the agent; nothing leaves without a person reading it. That setting is doing real security work and should stay.

Zoom Phone call logs — reachable, and the audit is unblocked

Working Pool write-back still needs the script
Works unattended
Download the pool from Drive (any size) → read it, whatever shape it arrives in → allocate contiguous 200-number blocks → repair leading zeros → build one workbook per caller → upload it into that caller's SharePoint folder. All built, all tested.
The one gap
Marking the source pool — shading used rows green and writing the high-water mark back. Two routes and both are shut:
Zoom, solved
Confirmed working 11 September. The agent can read the account's call logs and see who made which calls — the data the audit rests on. Three separate walls had to come down, and each looked like the previous one:
1. Licence
The Claude Zoom connector returns 403 "User does not have a valid license" — its search API needs a tier this account lacks, and Zoom Meetings fails identically. Its empty result sets were that same wall failing quietly. Not the route. Zoom's own Phone API is a separate entitlement, covered by the 53 Zoom Phone licences.
2. Credential
A Server-to-Server OAuth app with phone:read:admin, built in Brendon's own Zoom admin. Read-only on purpose: while this is being tested, nothing the agent does can change a caller's phone setup.
3. The one that cost the evening
Cloud sessions sit behind a network allowlist, and Zoom was not on it. CONNECT tunnel failed, 403 for zoom.us:443 — the request died before any credential was checked, so it looked exactly like a bad key. Fixed by a cloud environment set to Custom network access listing zoom.us and api.zoom.us. This should have been the first thing tested, before an hour went into building credentials.
And it is per environment
Not a switch that, once flipped, stays flipped everywhere. A session on 11 September held all three ZOOM_* variables and was still refused at CONNECT on both hosts — it simply was not started in the Custom environment. Having the credentials proves nothing about reachability. One curl settles it; a tunnel error is the wrong environment, not a bad key, and live-API work has to be started from the Custom one.
Two traps
Environment variables are copied in once, at container start, so the session that sets them can never see them — the work continues in a new one. And the settings gear does not appear on a running session's chip; the way through is Add cloud environment, whose creation form carries the same fields.

Measuring a shift from the call logs — built and tested

Working Thresholds need calibrating
What it does
business_agent/calllogs.py groups a day's Zoom Phone calls per caller and reports, for each: attempts, answered, talk time, completes, short answers, each break and their total, time actually worked, and how far short of a full shift. 55 tests, all of which run with no Zoom connection at all. This is the half of Elaine's audit that was manual.
Completes
Zoom cannot say whether a questionnaire was finished — only that someone picked up and stayed on. So length stands in for it: an answered call of 150 seconds or more counts as a complete. That is Brendon's figure and it is a parameter, not a law: too low and a polite refusal counts, too high and genuinely quick respondents are thrown away. Calibrate it against a week whose real completes are known.
The trap that drove the design
One of Pernelia's calls ran 6 minutes 27 seconds. Measuring the gap between one call starting and the next would have booked those six minutes as time away from the phone — punishing her for the longest conversation of the day. Breaks are therefore measured from the end of one call to the start of the next, and time inside a call is never idle however long it ran. Overlapping calls are handled with a running latest-end, so a short call finishing inside a longer one cannot invent a gap that never happened.
The idle floor
A gap under 60 seconds is not a break — it is hanging up, reading the next number and dialling. Counting those would make the fastest caller read as the idlest, because a fast caller has more of them. Brendon set the floor at 60s (it was 120s). Breaks are returned individually as well as totalled: three twenty-minute breaks and forty two-minute ones add to the same number and mean completely different things.
Three hours, not a clock window
A shift is three hours of calling, so lateness is not the measure — the length is. The clock starts at a caller's own first call, floored at 1:30pm Manila so one stray call at noon cannot run the three hours out before the work began, and it ends when the last call ends, not when it starts. Shortfall is measured against time worked rather than elapsed time, so three hours cannot be covered by one call, a disappearance and another call.
Run against a real day
Done, 11 September, across 1–11 September: 33,875 calls, 37 Zoom display names, and the Manila boundary correct — Pernelia's 10 September shift lands 13:25–16:26 Manila, inside the right date. Caller names come back on every outbound row. The three checks all pass.
Correction: completes were reading zero
A claim in this register was wrong, and wrong in the quietest possible way. ANSWERED in calllogs.py listed Connected, Answered and Call connected — a guess at Zoom's vocabulary. Against 11 days of live data two of those three never appear at all and the third caps at 7 seconds, so it is a dialler state and not a conversation. Every call with real talk time comes back as Auto Recorded, which the module was treating as unanswered.
The real values
Auto Recorded 15,669 (median 14s, max 2,841s) · Call Cancel 11,457 (all 0s) · Call connected 5,579 (median 3s, max 7s) · Call failed 5. On the old set the module scored 0 completes for every caller on every day, and talk_seconds and short_answers with it. The timing work — breaks, idle time, time worked, shortfall — never read answered and was never affected.
Now fixed
ANSWERED is {"Auto Recorded", "Connected", "Answered"}: Auto Recorded added, Call connected dropped — counting it would have invented 5,579 answered calls nobody ever spoke on — and the other two kept only for a tenant on a different API version. That gives 953 completes at 150s across the 11 days. Each value now has a test naming what it is, so the next person does not have to rediscover it. Left unfixed at first, deliberately, and that was the weaker call: the numbers it protected were all zero.
Still Brendon's to confirm
That Auto Recorded is what Zoom's own reporting calls answered. Everything downstream of it — completes, talk time, short answers — moves if it is not, and it is one line back. The timing figures never read it.
One more found
calls_for_day passed its default empty token straight to Zoom, so a real call sent Bearer  and came back 401 — which reads like a bad credential rather than a missing one, and would have cost someone an hour. It now mints its own token when no test stub is supplied.
On the 150s figure
It sits in a flat part of the curve, not on a cliff: 1,753 answered calls land 30–149s and 953 at 150s or more. Neither obviously right nor obviously wrong — still needs a week whose real completes are known.

And that one cannot be read
Graph refuses to extract it:
notSupported — Microsoft blocks conversion for applications that cannot decrypt the file. Per-file, enforced by Microsoft; retrying will not help unless the file or its label changes.
What that means
Normally an encrypting Purview sensitivity label. Brendon can still open the file in a browser under his own login — this is not a permissions problem, it is Microsoft declining to hand the bytes to an application. An earlier entry read the same notSupported as routine spreadsheet behaviour and concluded it "says nothing about whether Excel can open the file". That was right about Excel and wrong about the consequence: it is the reason the declared half of an audit cannot be read at all, and it is now a blocker rather than a curiosity.
Consequence for the audit
The audit compares what a caller declared against what the phone recorded. Zoom supplies the second half in full. The first half has no source: the sheets are mostly not there, and the ones that are cannot be opened. Until the label question is settled, declared numbers have to come from WhatsApp end-of-day or Curia's own reporting, not from these files.
Folder names carry the nickname
Pernelia Villapaz (Lia), Mary Joy Tongson (Mary T), Mary Joy Villacura (Mary V). A path built from the plain name 404s — five spellings were tried before the folder was found by listing rather than guessing. Never construct these paths; list the parent.
How to list it
read_resource on file:///{driveId}/root, then follow the item IDs. A single-segment path such as file:///{driveId}/Call Sheets is parsed as an item ID, not a path, and dies with invalidRequest — which reads like a broken drive and is not. Search is no help either: the tenant index holds one file from this whole site.

A SharePoint site is invisible until it holds something

Waiting on indexing
Why
The M365 connector finds sites only through the tenant search index — that is, through their contents. An empty site has no contents, so it cannot be seen at all, however correct its URL.
And it can't be looked up by URL
Asking for a site by address returns itemNotFound. That was worth proving rather than assuming: the same request against the old site, which certainly exists, failed identically. So the 404 says nothing about whether a site exists — the connector simply has no URL-to-site path. There is also no site-creation tool, so the site itself must be made by hand.
Consequence
A person has to create one folder by hand before the agent can build the other twenty. /sites/callsheets was created correctly and appeared after roughly two hours and eight sweeps — nothing was wrong, the index was simply slow. Budget hours, not minutes, before assuming a new site is misconfigured. Once visible, folder creation, cross-site copy and read-back all worked first time.

Spreadsheet contents are not searchable — and the upload was fine

Resolved Changes how files get found
Retracted
The uploaded call sheet was being reported as possibly corrupt and carried on the open list as unverified, on two pieces of evidence. Both were over-read. It never reached this register as a finding, and it is now closed.
The size difference
8,570 bytes sent, 17,170 reported. Normal. SharePoint repacks an xlsx on upload and adds its own document properties; a small workbook roughly doubling is expected. Truncation would come back smaller, not larger.
The extraction refusal
Graph returns notSupported for the file's text. That is the connector's extraction path failing, which it does routinely for spreadsheets — it says nothing about whether Excel can open the file. And Brendon had already opened it, which is the only test that counts.
The finding that does matter
A content search for Wellington Bays across the whole tenant returned old Zoom invoices and not the call sheet — despite it sitting in an indexed folder modified that morning. So spreadsheet contents are not searchable to the agent. Files can be listed and a sheet read when its location is already known, but a call sheet cannot be found by what is inside it. The agent must therefore track file locations itself rather than rediscovering them.
